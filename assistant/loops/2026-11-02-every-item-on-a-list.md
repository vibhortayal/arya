# 2026-11-02 Every item on a list (backend)

Owner, 2026-11-02: "whenever you add item to a list ... It should ask you to which list it should add it to. If you don't have any list, it should ask you to create a list before you add any items." Owner approved the "which list?" mockup and the one-list shortcut: with exactly one list, adds go straight to it.

- `api/routes/lists.py` `pick_list(list_id, item_id, names)`: the list named, else the list the item is already on, else the only list, else 409 with no write. `{"code": "pick_list", "message", "lists", "suggested", "names"}`, where `suggested` is the usual store's list (`state.usual_list`), or `{"code": "no_lists", "message", "names"}`. Typed names that are all on a list already stay where they are. Used by `/api/list/add` (by name and by item_id: Running low, Today, suggestions), `/api/list/from-text` (checked before any model call), `/api/list/import`, and `/api/list/from-photo`, which answers 200 with `needs_list` and the names, so the app adds them through from-text once a list is picked and there is no second photo read.
- Ask (`chat_service.apply_actions`): add_to_list and ran_out use the list named, the list on screen (context.list_id, now on every surface), the list the item is on, or the only list. Otherwise nothing is added and Ask asks "Which list should X go on: A, B?" (usual list first) or "Make a list first". The old "went to Everything else" fallback is gone (es and hi too).
- Connected agents: MCP `add_items` takes an optional `list` (name or id); without one, the error tells the agent to ask the user and names the lists. Lists API v1 refuses `unfiled` adds unless there is exactly one list.
- `/api/lists/delete`: a list with items answers 409 `list_has_items` (count, other lists) unless `move_to` or `remove_items`. The reply's `items` goes back to `/api/lists/restore` for Undo. Items also on another list just leave this one.
- Old rows: `/api/home` files list-less or deleted-list rows to the usual store's list, or the only list (`file_unlisted`). With two or more lists and no usual store, a row keeps no list until the person picks one (the UI shows these).
- Client: `ApiError.detail` carries the structured answer, and `friendlyError` reads its message. The picker, "Create a list first" sheet, delete choice and "Needs a list" card are the UI thread's PR, on top of this one.
- Offline queue (#412): compatible. The app picks the list before it queues an add. A queued add with no list that gets a 409 counts as failed and is reported by name. Only 2xx answers are kept as replays.

Tests: `tests/test_every_item_on_a_list.py` (no lists, one list, two lists then a pick, an item stays on its list, photo needs_list, old rows filed on read, unplaced rows wait, MCP list param). About 30 older tests now give their account one list (`tests/conftest.py one_list`) or name the list. The tests whose behaviour changed were rewritten: Ask with an unknown list asks, delete asks where items go, v1 unfiled, usual-store add suggests.
